# Отчёт №3

В данной работе выполнялись задания, связанные с репликацией сервера базы данных Postgres 16:
1) нагрузка на чтение: 1 сервер БД
2) нагрузка на чтение: 1 мастер-сервер и 2 слейв-сервера в режиме потоковой репликации, чтение выполнялось только со слейвов, маршрутизация на уровне приложения
3) нагрузка на запись: кворумная репликация, отключение одного из слейвов в процессе нагрузки, переключение мастера и последующее восстановление отключенного слейва
## Планы нагрузки
Все нагрузки выполнялись с помощью Apache JMeter с такими параметрами:
- 1 thread group
- 100 threads (users)
- ramp-up period: 1 second
- duration: 60 seconds
#### Нагрузка на чтение
Для создания тестовой нагрузки на чтение использовались 2 API endpoints:
- `GET /user/get/${randomUserId}` , где `${randomUserId}` – случайно сгенерированное число от 2 до 999932 (в рамках значений id пользователей в БД)
- `GET /user/search?first_name=Ма&last_name=Сам`, данный запрос находил ~230 пользователей; он использовался в предыдущем ДЗ
#### Нагрузка на запись
Для создания тестовой нагрузки на запись использовался следующий API endpoint:
```
POST /user/register`

{  
    "username": "${__UUID()}",  
    "password": "password",  
    "first_name": "Apache",  
    "second_name": "Jmeter",  
    "birthdate": "1990-12-21",  
    "biography": "Software, highload",  
    "city": "Moscow",  
    "gender": "male"  
}
```
Всего за период нагрузки в 1 минуту создавалось ~1900 пользователей (~31 RPS).

## Задание 2
Использовалась нагрузка на чтение, аналогичная заданию 1. Запущенные приложения:
- postgres: `psn1` (master)
- postgres: `psn2` (slave 2)
- postgres: `psn3` (slave 3)
- spring boot application
- apache jmeter
 
Режим репликации: **асинхронная потоковая репликация**.
Конфиг мастера:
```
wal_level = replica
```

В приложении настроен `ReplicationRoutingDataSource`, который умеет маршрутизировать запросы между 3 серверами БД: read-only запросы (выполняющиеся внутри `Transactional(readOnly=true)`) отправляются в слейвы, запросы на запись отправляются в мастер.

Время выполнения запросов:
- get по id: от 1120 мс до 1520 мс, в среднем 1320 мс; улучшение на 320мс (~20%)
- search по имени: от 720 мс до 860 мс, в среднем 790 мс; улучшение на 530мс (~40%)

## Задание 3
Для создания тестовой нагрузки на запись использовался следующий API endpoint:
```
POST /user/register`

{  
    "username": "${__UUID()}",  
    "password": "password",  
    "first_name": "Apache",  
    "second_name": "Jmeter",  
    "birthdate": "1990-12-21",  
    "biography": "Software, highload",  
    "city": "Moscow",  
    "gender": "male"  
}
```

Запущенные приложения:
- postgres: `psn1` (master)
- postgres: `psn2` (slave 2)
- postgres: `psn3` (slave 3)
- spring boot application
- apache jmeter
 
Режим репликации: **кворумная синхронная репликация**.
Конфиг мастера:
```
wal_level = replica
synchronous_commit = on
synchronous_standby_names = 'ANY 1 (psn2, psn3)'
```

Выполненные работы:
1. Нагрузка на запись создавалась в течение 30 секунд.
2. Примерно через 5 секунд после начала нагрузки `psn2` был выключен командой `docker stop`.
3. Ожидание завершения тестовой нагрузки.
4. `psn3` был настроен как новый master.
5. `psn1` был настроен как новый slave.
6. `psn2` перенастроен на новый `master` и теперь должен следовать за `psn3`. 
7. Запущены все сервера Postgres: `psn1`, `psn2`, `psn3`.
8. По логам убедился, что соединение серверов настроены корректно, `psn2` успешно начал следование за `psn3`.
9. На хосте `psn3` проверил статус репликации:
```sql
select application_name, sync_state  
from pg_stat_replication;

+----------------+----------+
|application_name|sync_state|
+----------------+----------+
|psn1            |quorum    |
|psn2            |quorum    |
+----------------+----------+
```
10. Проверил количество созданных во время нагрузки пользователей:
```sql
select count(*) from users.users  
where last_name = 'Jmeter';
```
На всех серверах `psn1`, `psn2`, `psn3` количество записей совпало.

#### Вывод
Остановка одной из реплик во время нагрузки на запись **не привело** к потере транзакций. После восстановления реплика **смогла получить недостающие транзакции** от мастера.
