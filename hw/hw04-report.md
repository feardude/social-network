# Схема приложения
![[hw04.drawio.svg]]

Вся логика реализована в одном монолитном сервисе. Все данные (пользователи, подписки/друзья, посты) персистентно хранятся в Postgres. Данные о постах и лентах постов дополнительно кэшируются в отдельно запущенном инстансе Redis. 

Лента постов у каждого пользователя своя, кэш `feed` выглядит так:
- **key**: `user_id`
- **value**: `zset<uuid>`
`ZSet` — упорядоченное множество id постов. В качестве ключа сортировки используется поле поста `created_at (timestamp)` – это позволяет хранить фид постов в отсортированном по времени создания порядке, чтобы было легко поддерживать размер фида на требуемом уровне (например 100 или 1000 ссылок).

В задании было требование поддерживать кэш фида на уровне 1000 постов, однако я для упрощения ограничил кэш фида 100 постами – генерация большего числа постов занимает много времени, к тому же все сервисы запускались локально на моём ноутбуке, и мне требовалось уместиться в память.

Сами посты также кэшируются в отдельной структуре:
- **key**: `post_id (uuid)`
- **value**: `post (json)`

Отдельный кэш постов позволяет избежать дублирования информации в фидах пользователей.

### Создание нового поста
При создании пользователем нового поста вызывается ручка `POST /posts`. Схема взаимодействия представлена на рисунке:
![[hw04-2.drawio.svg]]

Процесс добавления нового поста выполняется следующим образом:
1. Пользователь отправляет запрос на сервер с текстом нового поста.
2. Сервер сохраняет полученный пост в Postgres, которая запущена в режиме master-slave с двумя репликами в режиме кворумной синхронной репликации.
На этом синхронный запрос пользователя заканчивается, и он получает 200 OK. Далее сервер иницирует асинхронное обновление кэша в отдельном треде.
3. Сервер ищет всех подписчиков автора поста.
4. Сервер кэширует новый пост в Redis.
5. Сервер обновляет кэш фидов подписчиков с учётом времени создания поста. При этом из кэша удаляются id старых постов, если размер фида превышает предельный размер в 100 постов.

Асинхронное обновление кэша постов и фидов позволяет отделить процессы кэширования и создания поста, делая эти процессы независимыми. Также это увеличивает скорость запроса на создание поста для пользователя. При необходимости процесс перестройки кэша можно вынести в отдельную джобу, работающую по событию, или отдельный микросервис.

## Прогрев кэша при запуске приложения. Перестроение кэша через HTTP endpoint
### Прогрев
При запуске приложения по событию `ApplicationReadyEvent` в классе `PostCacheWarmupListener` запускается прогрев кэша. Он вызывает асинхронный метод `PostCacheWarmupService#warmupCache`, что позволяет сразу же приступить к обслуживанию HTTP запросов, и фоном начать заполнение кэша.

Стратегия выбора пользователей, для которых будет автоматически построен кэш: 
1. Приложение ищет всех пользователей, которые были активны в последние 14 дней.
2. Далее выбранные пользователи разбиваются на батчи по 1000 человек.
3. Каждый батч в 1000 человек за один запрос находит в Postgres все посты их друзей (подписок), не более 100 постов на каждого пользователя (функция `row_number()`).
В итоге в батче получаем 1000 пользователей, каждый со своим фидом постов.
4. Далее каждую пару `user_id + feed` добавляем в кэш Redis. Каждый пост из фида при этом также добавляется в кэш.

При этом кэш фида предварительно не стирается (если в кэше уже были какие-то значения до старта приложения, либо пользователь успел запросить свой фид параллельно с прогревом кэша), а обновляется, оставляя самые свежие 100 постов.

### Перестройка кэша через HTTP endpoint
Для перестройки кэша есть endpoint `POST /posts/cache`. Для простоты выполнения задания он не закрыт никакой аутентификацией и авторизацией, однако в проде подобную ручку стоит дать только пользователям с правами администратора.

Логика работы совпадает с прогревом кэша, так как endpoint вызывает метод `PostCacheWarmupService#warmupCache`.

## Инвалидация кэша
Записи в кэше (посты и фиды) могут храниться бесконечно долго. Вытеснение записей из кэша фида происходит при создании новых постов, если размер фида превышает 100 записей, а также при прогреве или принудительной перестройке кэша.


# Планы нагрузки
Все нагрузки выполнялись с помощью Apache JMeter с такими параметрами:
- 1 thread group
- 200 threads (users)
- ramp-up period: 1 second
- duration: 60 seconds
### Нагрузка на чтение
Для создания тестовой нагрузки на чтение использовался 1 API endpoint:
`GET /posts/feed` 

В качестве параметров использовались такие значения:
- `offset` – случайное значение в диапазоне [0, 150]
- `limit` – случайное значение в диапазоне [10, 100]
- `user_id` – случайный пользователь из списка топ-100 пользователей с наибольшими размерами фида (размер фида от 188 до 362 постов)

# Вывод
Сценарий с топ-100 пользователями наглядно показывает **влияние кэша** на получение фида пользователем. После загрузки фида в кэш **время ответа значительно падает** и на протяжение всего теста держится в пределах **35±5 мс**, что означает **ускорение в ~20 раз** по сравнению со сценарием чтения без кэша напрямую из Postgres (500-600 мс).

**Прогретый кэш** даёт снижение времени ответа по сравнению с холодным кэшом с 430 мс до 75 мс – **ускорение более чем в 5 раз**. Стратегия прогрева кэша может адаптироваться под реальные требования: можно изменить глубину выборки активных пользователей, поменять критерий выборки пользователей, а также разбить на отдельные батчи.

**Инвалидация кэша** выполняется при добавлении нового поста. Фид в кэше Redis хранится в структуре ZSet, что позволяет настроить упорядоченность постов в ленте по времени создания и легко выполнять вытеснение неактуальных записей, когда длина фида превышает заданный предел (в моём случае 100 записей).
